# 05 真实开发复盘

## 实际问题与处理

1. 原始目录没有代码、约定或 Git 仓库。先建立原生 Python 工程，用户指定新位置后检查目标与父目录约定，迁移新建文件并在目标重新建立虚拟环境。未把旧位置虚拟环境搬来复用。
2. 环境只有 Python 3.14.7。安装固定的 Pydantic、HTTPX、rank-bm25、pytest 成功，pip check 通过；NumPy 实际解析为 2.5.4，要求 Python >=3.12。因此依赖快照仅声明为本平台验证，不把 3.11 兼容性写成实测结论。
3. 首次 live 配置检查发现三个模型环境变量都缺失。保存 model_error/CONFIG_MISSING 及 run_id，继续离线验证；未搜索用户其他项目的密钥，也未降级成 Mock 报成功。没有取得两条真实路径，这是核心验收缺口。
4. 首次离线测试 33 passed、23 errors：Windows 已有共享 pytest 临时目录访问被拒。改为项目 work 下 UUID 临时目录；第一次修复漏建父目录，仍为 33 passed、23 errors，第二份失败日志也保留。补建父目录后 56 项通过；补充语义边界和无效语料预检测试后最终为 58 passed、1 deselected。
5. 早期 PowerShell 捕获中文显示乱码。CLI 输出流和后续采集子进程显式使用 UTF-8；JSON 产物本身始终用 UTF-8。原始失败日志保留其捕获状态，没有重写成伪造的干净日志。
6. 审查后补充：语料先预检，避免创建半份运行目录；失败 API 请求 metadata 保留可得请求 ID/实测耗时，未知 usage 为 null；空白引文拒绝。没有记录隐藏 reasoning 或密钥。

## 观察到的结果

相同执行器在脚本 Mock 下走过普通读取回答、冲突双方读取后补查、无资料改写检索、首次失败后新动作和持续失败停止。E09 将语料 30 改为 45，引用与回答同步变化；E10 新增 D02 后转为冲突澄清。这只能证明工具反馈、产物和执行边界可运行，不能证明真实模型会作出相同决策。

P1 使用可审阅短语归一化，没有增加第二套检索系统。固定 10 条小样本 Recall@3 从 0.80 到 1.00，冲突双文档召回从 2/3 到 3/3。标签与归一化由同一 AI 在开发中编写，保留查询也非外部盲测；不把此结果外推为生产性能。

## 技术认识与下一步

执行器的机械正确性与模型行为需要分别验证。已读原文、准确连续引文和引用 ID 能由程序检查；文档是否真支持某个解释、是否漏掉冲突，仍需要语义审查与真实模型结果。测试特意保留这一边界，不把字符串匹配说成事实一致性保障。

优先下一步：配置实际支持原生 tools 的模型，执行 E01–E07、E09–E10，保留失败和成功 Trace；至少人工审查普通与冲突两条真实路径。之后才考虑 Responses 适配、更多无关/歧义查询、注入样例、外部标注及跨平台 CI。没有进行多场景真实成本/时延、抗注入或大规模语料评估；后续已有一条正常Live的用量与延迟记录，不等于性能评估完成。
